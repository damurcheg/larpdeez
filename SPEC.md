# Техническая задача: простая личная образовательная платформа Larpdeez

## 1. Цель проекта

Создать простую личную образовательную платформу для хранения и прохождения собственных курсов, учебных материалов, заданий и отслеживания прогресса.

Проект должен быть простым для дальнейшего редактирования с помощью ИИ. Я не профессиональный программист: мне нужно иметь возможность открыть HTML-файл, найти нужный элемент и попросить ИИ изменить его, не разбираясь в сложной архитектуре.

**Приоритеты:**
1. Простота кода и структуры.
2. Надёжное сохранение данных между устройствами.
3. Бесплатный хостинг на Cloudflare Pages и база Cloudflare D1.
4. Понятная авторизация с самостоятельной первоначальной настройкой пароля.
5. Полная инструкция по запуску, настройке и обслуживанию в README.md.

## 2. Технологии и архитектура

Использовать:
- HTML для страниц.
- CSS для оформления.
- Vanilla JavaScript без обязательных фронтенд-фреймворков.
- Cloudflare Pages для размещения сайта.
- Cloudflare Pages Functions для небольшого количества серверных API-обработчиков.
- Cloudflare D1 для хранения данных.

Не использовать Node.js/Express в рабочем серверном окружении, отдельный сервер, Docker, ORM, сборщики и сложные системы модулей, если они не нужны для работы на Cloudflare Pages.

Не создавать сложную многоуровневую архитектуру, лишние абстракции, десятки файлов и избыточные зависимости.

Предпочтительная структура:

- `public/index.html` — главная страница.
- `public/login.html` — вход и первоначальная настройка пароля.
- `public/course.html` — просмотр курса и учебных материалов.
- `public/profile.html` — профиль и настройки.
- `public/css/style.css` — общие стили.
- `public/js/app.js` — общая логика интерфейса.
- `public/js/auth.js` — логика авторизации на клиенте.
- `public/js/course.js` — логика курса.
- `functions/api/` — только необходимые серверные обработчики.
- `migrations/0001_init.sql` — схема базы данных.
- `wrangler.jsonc` — конфигурация Cloudflare Pages и D1.
- `README.md` — подробная инструкция.
- `package.json` — минимальные необходимые команды и зависимости, если они действительно нужны.

Структуру разрешается немного изменить, если это объективно упрощает реализацию. Не создавать пустые файлы ради соблюдения списка.

## 3. Авторизация: пароль задаётся при первом использовании

Это критически важная часть проекта.

При первом открытии сайта база данных может быть пустой. В таком случае пользователю показывается экран первоначальной настройки:

«Добро пожаловать! Придумайте пароль для своей образовательной платформы».

Пользователь самостоятельно задаёт пароль и подтверждает его повторным вводом.

Требования:
- Не должно быть заранее заданного пароля.
- Не должно быть пароля `admin123` или любого другого пароля по умолчанию.
- Не требуется задавать `PLATFORM_PASSWORD` в Cloudflare.
- Не требуется задавать мастер-пароль через переменные окружения.
- При первом сохранении пароль надёжно хешируется на сервере и сохраняется в D1.
- В базе хранится только хеш и необходимые параметры хеширования, но не исходный пароль.
- После успешной настройки пользователь попадает в личный кабинет.
- При последующих открытиях сайта появляется обычная форма входа.
- После перезапуска, нового деплоя, очистки браузера или входа с другого устройства пароль должен оставаться прежним.
- Нельзя повторно показать первоначальную настройку или заменить пароль простым вызовом публичного API, если пароль уже установлен.
- Если пароль уже установлен, инициализация не должна автоматически перезаписывать его.
- В личном кабинете должна быть возможность изменить пароль после ввода текущего пароля.

### Безопасность авторизации

- Хешировать пароль на сервере с использованием PBKDF2-SHA256 через Web Crypto API либо другого совместимого с Cloudflare Workers надёжного алгоритма.
- Использовать случайную соль и достаточное число итераций.
- Создавать случайный идентификатор сессии и подписывать сессию криптографически надёжным способом.
- Хранить сессию в cookie с флагами `HttpOnly`, `Secure` для HTTPS и `SameSite=Lax` или строже.
- Реализовать выход из системы и аннулирование сессии.
- Для запросов, изменяющих данные, проверять авторизацию и защиту от CSRF.
- Ограничить частоту попыток входа, если это можно реализовать просто и надёжно.
- Не возвращать хеш пароля или секретные данные клиенту.
- Не считать скрытие HTML-страницы полноценной защитой: серверные API тоже должны проверять сессию.

### Сброс пароля

Предусмотреть понятный и безопасный способ восстановления доступа в README.

Не делать публичный API, который позволяет сбросить пароль без авторизации. Не создавать скрытые мастер-пароли, пароль по умолчанию или автоматический сброс при деплое.

Если восстановление через интерфейс невозможно без дополнительной инфраструктуры, честно описать ручной способ восстановления через D1, включая точные команды для администратора и предупреждение о последствиях. Не требовать скачивания проекта и установки дополнительных инструментов без необходимости. Никогда не удалять всю базу для сброса пароля.

## 4. Cloudflare D1

Использовать уже созданную базу данных:

- Имя: `larpdeez-data`
- Database ID: `2cbb429c-db4f-40d4-8eeb-968ced08d5d7`

Подключить её через binding `DB` в `wrangler.jsonc`.

Пример конфигурации:

```jsonc
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "larpdeez",
  "pages_build_output_dir": "public",
  "compatibility_date": "2025-06-01",
  "d1_databases": [
    {
      "binding": "DB",
      "database_name": "larpdeez-data",
      "database_id": "2cbb429c-db4f-40d4-8eeb-968ced08d5d7",
      "migrations_dir": "migrations"
    }
  ]
}
```

Проверь совместимость выбранной конфигурации с актуальным способом развёртывания Cloudflare Pages. Не заменяй имя и ID базы выдуманными значениями.

### Требования к D1

Создать минимально необходимую схему:
- настройки платформы;
- хеш пароля и состояние первоначальной настройки;
- профиль пользователя;
- курсы;
- учебные материалы;
- прогресс прохождения;
- задания и результаты, если они поддерживаются интерфейсом.

Не создавать таблицы для функций, которых нет в интерфейсе.

Все SQL-запросы должны использовать параметризованные выражения. При первом запуске пустой базы схема должна создаваться миграциями.

Приложение должно корректно работать с пустой базой и не предполагать, что в ней уже есть какие-либо записи.

## 5. Сохранение данных

Все важные данные должны храниться в D1, а не только в `localStorage`.

Обеспечить:
- сохранение созданных и изменённых курсов;
- сохранение материалов;
- сохранение прогресса;
- сохранение настроек и профиля;
- загрузку сохранённых данных после повторного входа;
- сохранение данных при переходе на другое устройство;
- понятную обработку ошибок при недоступности базы.

`localStorage` допустим только для необязательных настроек интерфейса, например темы или состояния бокового меню.

Не создавать фиктивное сохранение, когда интерфейс показывает успех, но запрос к базе не прошёл.

## 6. Интерфейс и личный кабинет

Сохранить существующий дизайн и функциональность проекта, если они уже есть. Не переписывать интерфейс с нуля без необходимости.

Сделать простой, аккуратный, современный интерфейс образовательной платформы.

Основные разделы:
- главная страница;
- список курсов;
- страница отдельного курса;
- материалы и задания;
- прогресс обучения;
- профиль и настройки;
- вход и первоначальная настройка пароля.

Не добавлять лишние функции ради демонстрации возможностей.

## 7. API и серверная логика

Создать только необходимые Cloudflare Pages Functions.

Предпочтительные операции:
- получить статус первоначальной настройки;
- задать пароль при первом использовании;
- войти;
- получить текущую сессию;
- выйти;
- сменить пароль;
- получить и изменить данные профиля;
- получить, создать, обновить и удалить курсы;
- получить и обновить прогресс;
- экспортировать и импортировать данные, если это предусмотрено интерфейсом.

Каждый endpoint должен иметь понятную ответственность. Не дублировать одну и ту же логику в нескольких местах.

Первоначальную настройку пароля реализовать атомарно или с защитой от гонки запросов: два одновременных запроса не должны позволить двум разным паролям по очереди стать первоначальным паролем.

## 8. README.md — обязательная подробная инструкция

README должен быть написан понятным русским языком для человека, который не умеет программировать.

Обязательно описать:

1. Что представляет собой проект и какие технологии использует.
2. Как работает первоначальная настройка пароля.
3. Как подключить существующую D1-базу `larpdeez-data`.
4. Как проверить `database_id` и binding `DB`.
5. Как настроить Cloudflare Pages через GitHub.
6. Какие значения указать для production branch, build command и build output directory.
7. Нужно ли оставлять build command пустым и почему.
8. Как применить миграции к удалённой D1-базе.
9. Как проверить, что таблицы созданы.
10. Как запустить сайт локально, если для этого требуется установка инструментов.
11. Как выполнять повторный деплой.
12. Как проверить ошибки Functions и D1.
13. Как менять пароль.
14. Как восстановить доступ при потере пароля.
15. Как экспортировать и резервировать данные.
16. Как безопасно обновлять проект через GitHub.
17. Какие файлы можно менять через ИИ, не затрагивая серверную логику.
18. Как устранить типичные ошибки: `no such table`, `unauthorized`, `bad-password`, неправильный binding, не применённая миграция.
19. Какие возможности бесплатного тарифа Cloudflare используются и какие есть ограничения.

Для каждого действия указать точные пункты меню Cloudflare или готовую команду. Не писать расплывчатое «настройте базу». Все команды должны соответствовать реальной структуре проекта.

Если операция требует терминала, прямо указать это. Не утверждать, что команду можно выполнить в браузере, если это не так.

## 9. Проверки перед завершением

Перед сдачей:
- проверить все файлы и импорты;
- проверить соответствие API и клиентского кода;
- проверить миграции на чистой базе;
- проверить первоначальную настройку пароля;
- проверить отказ в повторной настройке после установки пароля;
- проверить вход с правильным и неправильным паролем;
- проверить сохранение пароля после повторного деплоя;
- проверить сохранение курсов и прогресса после перезагрузки и повторного входа;
- проверить защиту API без сессии;
- проверить смену пароля;
- проверить выход из системы;
- проверить, что приложение не требует неизвестных секретов;
- проверить, что нет фиктивных функций, которые только имитируют работу.

Не заявлять, что тесты пройдены, если они фактически не запускались.

## 10. Ограничения

- Не добавлять обязательную авторизацию через внешние сервисы.
- Не требовать платных сервисов.
- Не использовать сервер Express или локальный SQLite для production.
- Не создавать сложную архитектуру без необходимости.
- Не добавлять лишние зависимости.
- Не хранить пароль в открытом виде.
- Не оставлять тестовый пароль по умолчанию.
- Не сбрасывать пароль при каждом деплое.
- Не удалять данные пользователя при миграции или обновлении.
- Не создавать дополнительные проекты Cloudflare или новые базы данных.
- Не менять существующую базу без объяснения и согласования.

## 11. Формат результата

Выполни изменения непосредственно в существующем репозитории GitHub.

В завершение предоставь:
1. Краткий список изменённых файлов.
2. Описание реализации первоначальной настройки пароля.
3. Инструкцию по первому запуску.
4. Список необходимых действий в Cloudflare.
5. Информацию о том, что проверено фактически, а что ещё нужно проверить после деплоя.

Главный критерий успеха: пользователь может открыть сайт, самостоятельно задать пароль при первом входе, затем пользоваться платформой с любого устройства, а пароль и данные сохраняются в D1 между деплоями без ручного сброса и сложных дополнительных скриптов.
